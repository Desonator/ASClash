> **ASClash (Advanced Simple Clash)** — приложение для управления прокси на OpenWrt от Desonator, основанное на [проекте SSClash от ZeroChaos](https://github.com/zerolabnet/SSClash).

<h3 align="center">Advanced Simple Clash — установка и настройка ASClash на OpenWrt</h3>

# Руководство по установке

## Скрипт автоустановки

Устанавливает или обновляет зависимости, пакет LuCI ASClash и ядро Mihomo.
Скрипт переносит старый пакет `luci-app-ssclash` на `luci-app-asclash` и
сохраняет конфигурацию и пользовательские данные в `/opt/clash`.

```bash
wget --no-proxy -qO- https://github.com/Desonator/ASClash/raw/refs/heads/main/install-asclash.sh | ash
```

## Установка вручную

## Шаг 1: Обновление списка пакетов

Обновите список пакетов, чтобы у вас были последние доступные версии.

Для **OpenWrt >= 25** (apk):

```bash
apk update
```

Для **OpenWrt < 25** (opkg):

```bash
opkg update
```


## Шаг 2: Установка необходимых пакетов

В общем случае пакетный менеджер подтягивает зависимости автоматически при установке из пакетного репозитория. В этом руководстве используется ручная установка из GitHub Releases, а необходимые зависимости такие:

- `coreutils-base64` — для скриптов, работающих с Base64;
- `kmod-tun` — модуль ядра для режима TUN;
- подходящий модуль прозрачного прокси в зависимости от стека файрвола:
  - `kmod-nft-tproxy` для **firewall4 / nftables**;
  - `iptables-mod-tproxy` для **firewall3 / iptables**.

Только если вы устанавливаете пакеты вручную (`.apk`/`.ipk`) или собираете собственный образ и какие‑то зависимости отсутствуют, вы можете установить модули прозрачного прокси вручную:

```bash
# Для nftables (firewall4) в OpenWrt >= 25:
apk add kmod-nft-tproxy

# Для nftables (firewall4) в более старых OpenWrt:
opkg install kmod-nft-tproxy

# Для iptables (firewall3, OpenWrt < 22.03.x):
opkg install iptables-mod-tproxy
```

## Шаг 3: Загрузка и установка пакета ASClash

Загрузите пакет ASClash и установите его. При ручном переходе со старого
пакета сначала остановите службу и удалите `luci-app-ssclash`; конфигурация и
пользовательские данные в `/opt/clash` сохраняются.

```bash
# OpenWrt >= 25:
/etc/init.d/clash stop 2>/dev/null || true
curl -L https://github.com/Desonator/ASClash/releases/download/v4.7.1/luci-app-asclash-4.7.1-r1.apk -o /tmp/luci-app-asclash-4.7.1-r1.apk
apk del luci-app-ssclash 2>/dev/null || true
apk add --allow-untrusted /tmp/luci-app-asclash-4.7.1-r1.apk

# OpenWrt < 25:
/etc/init.d/clash stop 2>/dev/null || true
curl -L https://github.com/Desonator/ASClash/releases/download/v4.7.1/luci-app-asclash_4.7.1-r1_all.ipk -o /tmp/luci-app-asclash_4.7.1-r1_all.ipk
opkg remove luci-app-ssclash 2>/dev/null || true
opkg install /tmp/luci-app-asclash_4.7.1-r1_all.ipk

rm -f /tmp/luci-app-asclash_4.7.1-r1_all.ipk /tmp/luci-app-asclash-4.7.1-r1.apk
```

## Шаг 4: Управление ядром

Откройте **Службы → ASClash → Статус → Управление ядром Mihomo**. Страница
определяет архитектуру роутера, проверяет установленный бинарный файл и
позволяет установить последний релиз из официального репозитория
`MetaCubeX/mihomo` или пользовательского GitHub-репозитория (например,
`legiz-ru/Prizrak-Core`). Перед проверкой и установкой выберите и сохраните
источник релизов. Установщик подбирает подходящий файл релиза, проверяет
установленный исполняемый файл и показывает установленную и последнюю версии.
После установки или обновления перезапустите службу Clash, чтобы запустить
новое ядро.

При первой установке пакета автозапуск службы намеренно отключён: сначала
можно проверить и отредактировать пример конфигурации. После подготовки
конфигурации запустите службу из LuCI (или выполните
`/etc/init.d/clash enable`); после этого она будет запускаться при следующих
перезагрузках роутера.

Индикаторы состояния периодически проверяют службу init и запущенный процесс
`/opt/clash/bin/clash`. Страница обновляется при обнаружении изменения статуса
службы или ядра. Проверка конфигурации учитывает выбранное ядро; для
Prizrak-Core используется валидатор настроенного источника, чтобы стандартный
валидатор Mihomo не отклонял специфичные для Prizrak параметры.


## Шаг 5: Настройка обработки трафика

ASClash предлагает два режима обработки интерфейсов:

### Режим исключения (Универсальный подход) - **Рекомендуется для большинства пользователей**

* **Режим по умолчанию**, который обрабатывает трафик со ВСЕХ интерфейсов, кроме выбранных
* Автоматически определяет и исключает WAN-интерфейс
* Прост в настройке - просто выберите интерфейсы для обхода прокси
* Лучше всего подходит для типичных домашних роутеров


### Явный режим (Точный контроль) - **Для продвинутых пользователей**

* Обрабатывает трафик ТОЛЬКО с выбранных интерфейсов
* Более безопасен, но требует ручной настройки
* Автоматически определяет LAN-мост при включении
* Идеально подходит для сложных сетевых конфигураций, требующих точного контроля


### Дополнительные настройки:

* **Блокировать QUIC-трафик**: Блокирует UDP-порт 443 для повышения эффективности прокси для таких сервисов, как YouTube
- **Хранить правила и proxy-providers в RAM**: Каталоги rulesets и proxy-providers размещаются в tmpfs для сохранения ресурса NAND-чипа
- **Добавить HWID-заголовки к подпискам**: Автоматическое добавление HWID-заголовков к proxy-providers (совместимость с Remnawave)

Поддерживаются режимы прокси TPROXY, TUN и MIXED. В режиме MIXED TCP
обрабатывается через TPROXY, а UDP — через TUN. Для режима TUN необходимы
`/dev/net/tun` и пакет `kmod-tun`; для режима прозрачного прокси нужен
соответствующий модуль TPROXY для используемого файрвола. В TUN/MIXED также
настраиваются правила forwarding и policy routing для интерфейса `clash-tun`.
Стек TUN (`system`, `gvisor` или `mixed`) задаётся в YAML-конфигурации Mihomo.

# Сетевое поведение и генерируемые IP-CIDR-списки

### Выбор интерфейсов и трафик вне прокси

В режиме интерфейсов **Исключение** обрабатывается трафик выбранных интерфейсов,
кроме исключённых (при включённом автоопределении WAN обнаруживается и
исключается автоматически). В режиме **Явный** обрабатываются только выбранные
интерфейсы. Правила файрвола также пропускают зарезервированные/локальные сети,
IP прокси-серверов, порты Clash и уже помеченный маршрутизационными метками
трафик, предотвращая петли. Файрвол определяет, какие соединения передаются в
Mihomo; окончательное действие для попавшего в ядро трафика определяется
конфигурацией Mihomo и порядком его правил.

### Whitelist Fake-IP (обычный список IP-CIDR)

Если `dns.fake-ip-filter-mode` установлен в `whitelist` или `rule`, файрвол
может помечать трафик к IPv4-адресам и подсетям из
`/opt/clash/lst/fakeip-whitelist-ipcidr.txt`. Страница статуса LuCI показывает
сводку по provider-ам и FAQ. Файл поддерживает ручные записи и автоматически
генерируемую область между маркерами `AUTO-BEGIN`/`AUTO-END`; ручное содержимое
за пределами маркеров сохраняется. Генератор берёт IPv4-записи `IP-CIDR` из
provider-ов, на которые ссылаются правила не `DIRECT`/`REJECT`, соответствующие
записи `RULE-SET` из `dns.fake-ip-filter`, а также inline-правила `IP-CIDR` с
действием не `DIRECT`, `REJECT`, `REJECT-DROP` или `PASS`. Чтобы отключить
генерацию и управлять списком вручную, задайте
`AUTO_FAKEIP_WHITELIST=false` в `/opt/clash/settings`. Изменения применяются
файрволом без перезапуска Mihomo.

В режиме `whitelist` fake-IP выдаётся только DNS-именам, выбранным Mihomo.
В режиме `rule` список `fake-ip-filter` проверяется сверху вниз и для каждого
совпадения выбирает `fake-ip` или `real-ip`. Адреса fake-IP маршрутизируются по
fake-IP-диапазону; реальные адреса попадут в Mihomo только при совпадении с
сгенерированным/ручным CIDR-списком или другими правилами файрвола. Динамические
DNS-ответы для доменных правил `real-ip` нельзя надёжно превратить в статические
IP-наборы, поэтому такой трафик может обходить ядро, если не покрыт отдельно.

### Группированные AND-правила IP-CIDR (только nftables)

Для поддерживаемых `AND`-правил, объединяющих provider или прямые IPv4-записи
`IP-CIDR` с `NETWORK` и/или `DST-PORT`, ASClash создаёт отдельные IPv4-наборы
nftables и компактные правила маркировки по протоколу/порту. Диапазоны портов
остаются диапазонами, CIDR не разворачиваются в пары IP/порт. Функция работает
только с nftables; grouped AND-правила не применяются в iptables-ветке. На
странице статуса отображаются provider, сеть, порты назначения и число записей;
также есть FAQ.
Если в AND-правиле несколько CIDR-условий, сгенерированный набор содержит их
пересечение, а не объединение. Правила с итоговым действием `DIRECT`, `REJECT`
или `REJECT-DROP` пропускаются при генерации grouped firewall-наборов. Остальные
действия помечаются для передачи в Mihomo, где ядро продолжает проверку правил.
Одинаковые итоговые CIDR-наборы используются совместно правилами с разными
условиями сети/портов; сами правила nftables остаются отдельными. В таблице
статуса каждый provider показан один раз, его сети и условия портов объединены,
а счётчик показывает уникальные CIDR именно этого provider-а. Общий итог при
этом учитывает каждый уникальный объединённый firewall-набор только один раз.
Grouped-правила обрабатывают подходящий транзитный трафик; для трафика самого
роутера действует отдельная политика output-цепочки, и эти наборы на неё не
распространяются.

Генерация включена по умолчанию и ограничена параметрами
`GROUPED_FAKEIP_MAX_GROUPS=32` и `GROUPED_FAKEIP_MAX_CIDRS=150000`. При
превышении лимита генерация завершается ошибкой вместо применения слишком
большого сгенерированного набора. `GROUPED_FAKEIP_PORT_RULES_DRY_RUN=true`
генерирует и проверяет batch, но не применяет grouped-набор. Digest исходных
данных и batch позволяет не выполнять повторный разбор и не менять файрвол без
необходимости; параллельные обновления сериализуются lock-файлом. Данные,
зависящие от provider-ов, обновляются после запуска ядра и появления файлов
provider-ов, при поднятии WAN и cron-задачей каждые 30 минут. При отсутствии
изменений источников правила файрвола повторно не собираются.

### Веса Smart-групп

На странице «Статус» ASClash находит группы с `type: smart` и запрашивает их
уникальные серверы и веса через API `external-controller` ядра. Каждая группа
показывается отдельно; карточки серверов сортируются по текущему весу и
окрашиваются от красного (низкий вес) через жёлтый к зелёному (высокий вес).
Значения обновляются в браузере каждые 30 секунд, пока страница открыта и
видима. Секция не отображается, если Smart-групп нет или ядро не предоставляет
необходимый API. Запрос весов выполняет LuCI-бэкенд на роутере, поэтому
настроенный `external-controller` должен быть доступен с роутера. Если задан
секрет доступа, настройте его в конфигурации.

## Пример grouped `AND`-правил

Например, поддерживается такое правило: оно ссылается на IP-CIDR provider и
ограничивает firewall-метку диапазоном UDP-портов назначения:

```yaml
- AND,((RULE-SET,cloudflare-ip),(DST-PORT,80,443,2052,2053,2082,2083,2086,2087,2095,2096,8080,8443,8880)),Подсети IP-CIDR
- AND,((RULE-SET,discord-voice),(NETWORK,udp),(DST-PORT,50000-50100)),Discord
- AND,((IP-CIDR,186.157.42.56/32),(NETWORK,tcp),(DST-PORT,80,443,2050-2100,8080-8880)),Подсети IP-CIDR
```

Следующие параметры в `/opt/clash/settings` управляют созданием batch (это не
замена собственному механизму обработки правил Mihomo):

```sh
GROUPED_FAKEIP_PORT_RULES_ENABLED="true"
GROUPED_FAKEIP_PORT_RULES_DRY_RUN="false"
GROUPED_FAKEIP_MAX_GROUPS="32"
GROUPED_FAKEIP_MAX_CIDRS="150000"
```

Проверить синтаксис созданного nft batch без его применения можно так:

```sh
nft -c -f /tmp/clash/fakeip_port_groups.nft
```

# Удаление ASClash

Чтобы полностью удалить пакет ASClash:

```bash
# OpenWrt >= 25:
apk del luci-app-asclash

# OpenWrt < 25:
opkg remove luci-app-asclash
```

Для удаления пакета не нужно удалять `/opt/clash`: там находятся конфигурация,
подписки и пользовательские данные. Удаляйте этот каталог вручную только если
намерены стереть их полностью.
